# Runbook.md — 장애 대응 절차

> functional-spec.md의 예외 처리 표를 운영 관점 대응 절차로 옮긴 템플릿입니다. 실제 인프라/알림 채널이
> 정해지면 "대응 절차" 칸을 구체화합니다.

| 상황 | 관련 에러코드 | 시스템 동작 | 대응 절차(TBD) |
|---|---|---|---|
| 외부 트렌드/소셜 API 응답 지연·장애 | `SERVER_002` | 캐시 데이터 + "갱신 지연" 배지로 노출 | 담당자 확인 → 외부 API 상태 페이지 확인 → 장기화 시 [Incident_Log.md](Incident_Log.md) 기록 |
| Spike Score 배치 실패(원본 데이터 수집 실패) | `SERVER_003` | 이전 캐시 유지, 관리자 알림 발송 | 배치 로그 확인 → 원인(rate limit/인증만료 등) 파악 → 수동 재계산(ADMIN-001) |
| 배치 중복 실행 감지 | `VALID_003` | 스킵 후 로그만 기록 | 정상 동작 — 스케줄러 중복 트리거 원인만 주기적으로 점검 |
| 이메일 알림 발송 실패(SMTP 오류) | `SERVER_005` | 최대 3회 재시도 후 실패 처리, 인앱 알림은 유지 | SMTP 자격증명/쿼터 확인 → 재발 시 발송 서비스 상태 점검 |
| 리포트 생성 처리 시간 초과 | `SERVER_004` | 비동기 처리로 전환, 완료 시 인앱 알림 | 대기열 적체 여부 확인 → 필요 시 워커 스케일 조정 |

# API_Design.md — API 설계 및 외부 연동 규칙

> 공통 규칙은 [../CLAUDE.md](../CLAUDE.md) 참고. 원본 API 계약은
> [../TrendFit-ux-docs/functional-spec.md](../TrendFit-ux-docs/functional-spec.md) 참고. 성능 공통 원칙은
> [Coding_Convention.md](Coding_Convention.md) §4도 참고.

## 1. 내부 API 설계 원칙

- 엔드포인트는 자원(리소스) 중심, `/api/v1/{resource}` 형태로 설계합니다 (예: `/api/v1/dashboard/keywords`).
- `functional-spec.md`에 이미 정의된 엔드포인트는 그 계약(요청/응답 필드명, 경로)을 우선 따릅니다. 구현 중
  불가피하게 계약을 변경해야 하면 먼저 이유를 설명하고 사용자 확인 후, 이 문서의 §6에 실제 기준을 기록합니다.
- API 계약(요청/응답 스키마)은 `models/`에 Pydantic 모델로 정의하고 `api/`·`services/`에서 재사용합니다.

## 2. 공통 응답 포맷

성공/실패 스키마를 프로젝트 전체에서 통일합니다 (functional-spec.md의 각 엔드포인트 예시와 일치):

```json
// 성공
{ "success": true, "data": { }, "meta": { } }

// 실패
{ "success": false, "error": { "code": "VALID_001", "message": "관심 분야를 1개 이상 선택해주세요." } }
```

- `meta`는 페이지네이션(`page`, `total`, `nextCursor`) 등 부가 정보가 있을 때만 포함합니다.
- 실패 응답의 `error.message`는 **사용자용 메시지**이고, 내부 원인(스택트레이스, 요청 컨텍스트)은 로그에만
  남깁니다([Coding_Convention.md](Coding_Convention.md) 에러 처리 원칙과 연결).

## 3. 공통 에러 코드 표

`functional-spec.md`의 각 기능별 예외 처리 표에 흩어져 있던 에러 코드를 아래로 통합합니다. 신규 에러 코드가
필요하면 이 표에 먼저 등록한 뒤 사용합니다(코드 난립 방지).

| 코드 | 의미 | 사용 예 |
|---|---|---|
| `VALID_001` | 필수 값 미선택/미입력 | 관심 분야·플랫폼·수신 채널 미선택 |
| `VALID_002` | 잘못된 값/파라미터 형식 | enum 범위 밖 값, 잘못된 기간 파라미터 |
| `VALID_003` | 비즈니스 규칙 위반 | 키워드 중복 등록, 최대 등록 개수 초과, 배치 중복 실행 |
| `RES_001` | 요청한 리소스/데이터가 없음 | 존재하지 않는 키워드 ID, 관심 분야 데이터 없음 |
| `RES_002` | 데이터가 부족해 처리 불가 | 신생 분야라 리포트 생성 불가 |
| `RES_003` | 리소스가 만료/삭제됨 | 삭제된 콘텐츠 원문 링크 |
| `SERVER_001` | 네트워크 오류 | 클라이언트-서버 간 통신 실패 |
| `SERVER_002` | 외부 데이터 소스 지연/장애 | 캐시 데이터 + "갱신 지연" 배지로 대체 |
| `SERVER_003` | 배치 작업 중 원본 데이터 수집 실패 | Spike Score 배치의 외부 API 실패 |
| `SERVER_004` | 처리 시간 초과 (비동기 전환) | 대용량 리포트 생성 지연 |
| `SERVER_005` | 발송 실패 | 이메일(SMTP) 알림 발송 실패 |

## 4. 외부 API 연동 원칙

- 외부 API 키/시크릿은 코드에 하드코딩하지 않고 환경변수 또는 `.streamlit/secrets.toml`(또는 배포 환경의
  시크릿 매니저)로 관리합니다.
- 외부 API 호출 로직은 `services/`에 모듈화하여, 호출부(`api/routers`, `worker/jobs`, 페이지)가 API
  세부사항을 알 필요 없게 합니다.
- 요청 제한(rate limit)이 있는 API는 `config/`에 호출 주기/최대 호출 수를 상수로 정의합니다.

## 5. 성능 원칙

- **동일한 요청/연산을 반복하지 않습니다.** 동일 키워드/분야에 대한 재조회는 캐시를 우선 사용합니다.
- **API 호출을 최소화**합니다 — 배치 조회가 가능한 경우 개별 호출 대신 배치로 처리합니다.
- 캐시 유효기간(TTL)은 데이터 특성에 맞게 `config/`에서 관리합니다. 대시보드 데이터는 NFR-PERF-002(1시간
  이내 반영)를 만족하는 선에서 캐시하고, 서버 갱신 시각을 `meta.updatedAt`으로 함께 반환합니다.
- 대용량 응답은 Pagination(`cursor` 방식, CURATE 계열) 또는 페이지 번호(`page`, DASH 계열)를 적용합니다.

## 6. 실패 처리

- 외부 API 실패 시 즉시 전체 기능을 중단하지 않고, 어떤 부분 데이터가 유효한지 구분해서 처리합니다.
- 외부 API 원인의 에러는 로그에 요청/응답 컨텍스트를 남기고, 사용자에게는 `SERVER_002` 수준의 메시지와
  이전 캐시 데이터를 함께 제공합니다(NFR-SCALE-001 캐시 폴백).
- 배치 작업(Spike Score, 알림 발송)이 실패하면 이전 캐시/결과를 유지하고 관리자에게 알립니다(`SERVER_003`).

## 7. 신규 외부 연동 추가 시 체크리스트

1. `services/`에 전용 모듈로 분리했는가
2. 인증 정보를 하드코딩하지 않았는가
3. 호출 제한/캐싱 정책을 `config/`에 정의했는가
4. 실패 시 사용자 메시지(§3 에러코드)/로그 메시지를 분리했는가
5. 아래 §8 "연동 현황"에 실제 구현 내용을 추가했는가 (실제 호출로 확인한 제약/주의사항 포함)

## 8. 연동 현황

SRS §5.2에서 정의한 외부 연동 목록입니다. 아직 구현 전이며, 각 연동을 실제로 붙일 때 이 표(및 아래 항목)를
**실제 호출로 확인한 사실 기준**으로 채웁니다(추측 금지 — [Data_Rules.md](Data_Rules.md) §1 참고).

| 연동 | 용도 | 상태 |
|---|---|---|
| 네이버 데이터랩 API | 검색어 트렌드 데이터 수집 | 미구현 |
| 구글 트렌드(Trends) | 검색어 트렌드 데이터 수집 (공식 API 없음 — 비공식 라이브러리 검토 필요) | 미구현 |
| 유튜브 데이터 API | 영상 콘텐츠 및 언급량 수집 | 미구현 |
| X(트위터) API | 소셜 언급량·감성 데이터 수집 | 미구현 |
| 포털 뉴스 검색 API | 뉴스 기사 수집 | 미구현 |
| 구글/카카오 소셜 로그인 | OAuth 2.0 인증 (FR-AUTH-002, P2) | 미구현 |
| 이메일 발송 (SES/SMTP) | 급상승 알림, 인증 메일 발송 | 미구현 |

각 연동을 구현할 때는 아래 형식(블로그 프로젝트 선례)으로 항목을 추가합니다:

```
### <연동명>
- 모듈: `services/<client>.py`
- 용도: ...
- 인증: ...
- 캐싱: ...
- 실패 시: ...
- 실제 호출로 확인한 제약/주의사항: ...
```
